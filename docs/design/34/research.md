## 레퍼런스 4개

공개 화면을 Chromium에서 열어 확인했다. 로그인 후 실제 계정 화면을 사용한 것은 아니다.
CSS 글꼴 이름은 브라우저의 computed style로 확인한 선언값이며 모든 문자의 실제 렌더링 글꼴을 뜻하지 않는다.
아래 수치와 디자인 제안은 관찰을 토대로 정한 차곡의 후보 값이다. 다른 서비스의 디자인 토큰을 그대로 복제한 것이 아니다.

### 1. 우리의식탁 — 사진과 조리 내용 사이의 여백

- 출처: [레시피 목록](https://wtable.co.kr/recipes), [땡초김밥 상세](https://wtable.co.kr/recipes/314wwQZR5hXP4RMCEKzJMHfa).
- 확인 화면: [목록](references/wtable.png), [상세의 재료·단계](references/wtable-ingredients.png).
- 관찰: 이미지와 짧은 제목의 묶음, 충분한 바깥 여백, 재료와 단계의 명확한 구분. 목록의 영문 섹션 제목은 `Noto Serif KR` 선언, 관찰 당시 약 23.4px였다.
- 적용 제안: A의 사진 비율 8:5, 카드 간격 24px, 상세 재료/단계 분리. 장문 본문은 Sans 16px/1.85로 읽기 편하게 한다. 외국어 대문자 섹션명은 차곡의 필수 탐색 문구에 쓰지 않는다.
- 한계: 사진 중심 구성을 그대로 쓰면 사진 없는 항목이 큰 빈 영역이 된다. 차곡에서는 기본 표지 높이를 줄이는 조합도 검토한다. 서비스의 명조·프로모션·쇼핑 영역은 그대로 적용하지 않는다.

### 2. 만개의레시피 — 재료명과 분량을 나란히 읽기

- 출처: [마늘종 간장볶음 상세](https://www.10000recipe.com/recipe/6877464).
- 확인 화면: [재료 영역](references/10000recipe-ingredients.png).
- 관찰: 재료 이름과 분량의 짝, 조리 단계 구분. 제목 영역의 computed style은 `Noto Sans KR`, 34px였다.
- 적용 제안: 이름은 왼쪽, 분량은 오른쪽으로 정렬하고 행마다 구분선을 둔다. 숫자·g·ml·℃·½큰술이 섞여도 줄이 겹치지 않게 한다. 미기재는 값의 부재로 표시한다.
- 한계: 검색 포털의 높은 정보 밀도와 광고 배치는 개인 보관함에 옮기지 않는다. 원문 재료 정보가 없는 링크에는 재료 표를 만들어내지 않는다.

### 3. Raindrop.io — 작은 썸네일과 출처가 있는 목록

- 출처: [공식 소개 페이지의 제품 화면](https://raindrop.io/).
- 확인 화면: [공식 페이지에 표시된 보관함 예시](references/raindrop.png).
- 관찰: 사이드바와 본문 분리, 작은 썸네일, 제목 아래 출처·설명. 공식 데모 이미지 관찰이며 로그인한 보관함의 실제 조작 검증은 아니다. 소개 페이지 제목은 시스템 Sans 계열, 50px 선언이었다.
- 적용 제안: B의 PC 132px/모바일 86px 썸네일, 출처·제목·짧은 설명 순서. PC는 필터 사이드바를 쓰고 모바일은 상단 필터로 전환한다. 글만 있는 항목에도 같은 목록 구조를 쓴다.
- 한계: 너무 촘촘하면 긴 한글 제목을 구별하기 어렵다. 제목은 최대 두 줄, 카드 전체를 하나의 큰 버튼으로 만들지 않고 상세 링크와 즐겨찾기를 각각 조작하게 한다.

### 4. Notion — 긴 글 편집에서의 구분과 절제

- 출처: [한국어 위키 소개의 제품 예시](https://www.notion.com/ko/product/wikis).
- 확인 화면: [제품 탐색/편집 예시](references/notion-product.png).
- 관찰: 제목 굵기와 문서 블록의 정렬, 사이드바의 탐색 분리. 소개 페이지의 제목 선언은 `NotionInter, Inter, ...`, 64px였다. 한글 실제 glyph가 Inter라고 단정하지 않는다. 제품 예시와 공개 소개 화면을 관찰했으며 비공개 편집기를 사용한 것은 아니다.
- 적용 제안: 입력 폼을 ‘가져온 내용’과 ‘저장할 내용’ 두 구역으로 나누고 항상 보이는 label을 둔다. PC는 두 열, 모바일은 위아래. 제목 입력은 여러 줄로 보여 긴 제목도 검토할 수 있게 한다.
- 한계: Notion의 블록 에디터·협업·복잡한 사이드바는 이번 범위에 필요하지 않다. 정리 결과 변경이 보존 원문을 덮어쓰지 않는 기존 동작을 유지한다.

## 글꼴과 공통 기준 후보

| 기준 | A | B |
| --- | --- | --- |
| 본문 글꼴 | Pretendard 400 | Noto Sans KR 400 |
| 제목·선택 상태 | 600, 워드마크 700 | 600, 워드마크 700 |
| PC 화면 제목 | 36px / 1.35 | 32px / 1.35 |
| 모바일 화면 제목 | 28px / 1.35 | 28px / 1.35 |
| 카드 제목 | 18px / 1.5, 최대 2줄 | PC 17px, 모바일 15px / 1.6, 최대 2줄 |
| 조리 본문 | 16px / 1.85 | 16px / 1.85 |
| 입력값 | 16px / 1.7 | 16px / 1.7 |
| 모서리 | 카드 18px, 입력 8px | 카드 8px, 입력 8px |
| 구조 | PC 카드 3열, 태블릿 2열, 모바일 1열 | PC 필터+목록, 모바일 목록 |

- 긴 제목은 목록의 표시만 두 줄로 제한한다. 상세는 전체 제목을 노출하고 제목 편집은 textarea로 확인한다. 원본 문자열을 잘라 저장하지 않는다.
- 긴 한글은 기본적으로 단어 단위로 줄바꿈하며, 긴 URL/붙어 있는 문자열은 영역을 넘지 않게 개행한다.
- 원문·출처·미기재·확인 필요를 장식 색상만으로 구분하지 않는다. 본문과 label은 명시적으로 적는다.
- 버튼과 필터는 최소 높이 44px, 키보드 초점은 3px 외곽선. CSS 전환은 짧게 하고 reduced-motion을 지원한다.
- 비교용 폰트에는 `font-synthesis:none`을 적용했다. 현재 고운돋움은 기존 Regular 400 파일이며 굵기 계층 비교에 불리하다. Pretendard와 Noto는 실제 400/500/600/700 face 로딩을 확인했다.

### 라이선스·크기·로딩

- [Pretendard v1.3.9](https://github.com/orioncactus/pretendard/tree/v1.3.9): [SIL OFL 1.1](https://github.com/orioncactus/pretendard/blob/v1.3.9/LICENSE). 시안은 해당 버전의 dynamic-subset CSS를 사용한다.
- [Noto Sans KR](https://fonts.google.com/noto/specimen/Noto+Sans+KR): [Noto CJK Sans의 SIL OFL 1.1](https://github.com/notofonts/noto-cjk/blob/main/Sans/LICENSE). 시안은 Google Fonts CSS를 사용한다. 버전 고정·파일 동봉은 실제 적용 단계에서 한다.
- 현재 GowunDodum은 저장소의 445,620바이트 WOFF2와 기존 `app/fonts/OFL.txt`를 사용한다.
- 같은 브라우저 세션에서 화면·글꼴을 순회하며 Resource Timing의 encodedBodySize 합계를 확인했다: Pretendard 464,028바이트, Noto 348,020바이트, 고운돋움 445,620바이트. 이는 이 예시의 사용 문자·굵기에서 내려받은 부분집합 합계이며 전체 배포 파일 크기·전송 헤더·동일 조건의 cold-load 성능 비교가 아니다.
- 시안은 네트워크가 있어야 새 글꼴과 공개 사진을 가져온다. 실제 앱 적용은 설치된 Next.js 16.4 문서 `node_modules/next/dist/docs/01-app/03-api-reference/02-components/font.md`에 따라 로컬 폰트와 fallback metric 조정·preload를 결정한다. 필요한 face만 동봉하고 OFL을 함께 보관한다.
- 글꼴 로딩 완료 후 렌더링은 확인했지만 느린 네트워크에서의 CLS와 실제 앱의 전환 성능은 아직 측정하지 않았다. 글꼴 변경만으로 CLS가 해결됐다고 보지 않는다.

## 데이터의 출처와 한계

- 사진이 있는 항목은 실제 공개 우리의식탁 ‘땡초김밥’이다. 사진 URL과 출처를 명시하고 클릭하면 원본으로 이동한다. 이미지 파일이나 레시피 본문을 복사해 배포하지 않았다. 서비스 적용용 자산으로 채택한 것은 아니다.
- ‘고구마 누룽지’와 ‘감자 수프’는 저장소 `tests/unit/normalize-item.test.ts`의 테스트 원문을 사용했다. 고구마의 분량·시간·온도는 추측하지 않았다.
- 매우 긴 제목과 단위/장문 specimen은 **표시 검증용으로 작성한 예시**다. 실제 Instagram 게시물에서 수집한 제목이나 레시피라고 주장하지 않는다.
- 비교 데이터는 A/B에서 동일하다. 개인 계정 데이터나 비공개 첨부는 사용하지 않았다.

## 추천과 선택할 사항

추천은 **A의 아이보리·올리브와 Pretendard에 B의 목록 밀도를 조합하는 방향**이다. 차곡의 부드러운 인상을 유지하면서 글만 저장한 항목도 찾기 쉽다. 사진이 없는 목록을 큰 기본 표지로 채우는 A의 단점도 줄일 수 있다. 현재 비교 화면에는 순수 A/B를 보여 주며 조합안은 아직 구현하지 않았다.

사용자가 A, B 또는 조합 방향을 선택한 뒤 실제 공통 스타일을 적용한다. 이 단계는 이슈 #34의 ‘같은 콘텐츠의 시안으로 방향을 정한 뒤 구현’ 순서를 따른다.

## 후속 구현 범위와 완료 기준

1. 확정한 폰트·색상·크기·간격·반응형 기준을 공통 CSS와 layout에 적용.
2. 기존 ItemCard·보관함 검색/필터·상세·ItemForm·로그인/안내·첨부/사진 선택으로 확장. UI용 시안을 그대로 제품의 데이터 구조로 쓰지 않는다.
3. 실제 SNS 긴 제목, 긴 본문, 사진 유무, 원문 근거, 미기재, 로딩·빈 결과·오류·선택·초점 상태 확인.
4. 기존 저장·검색·수정·대표 사진 선택·실패 시 입력 보존 검증, 필요한 typecheck/lint/unit/build와 관련 실제 연결 E2E 실행.
5. 느린 폰트 로딩/CLS, 320px·일반 휴대폰·태블릿·PC·확대·키보드·스크린리더와 대비 확인. 전후 화면 기록.
6. #34의 미완료 조건을 갱신하고 사용자 리뷰용 PR 전달. 이번 조사 PR은 #34를 닫지 않는다.
