# 차곡 무료 우선 다중 사용자 설계

작성일: 2026-10-09
상태: 기획 승인 완료, 구현 전 설계

## 1. 목적

차곡은 흩어진 정보를 다시 찾고 읽기 쉽게 보관하는 모바일 웹서비스다. 첫 사용 사례는 요리·베이킹 레시피지만, 데이터와 화면은 다른 정보 유형으로 확장할 수 있게 만든다.

초기 성공 기준은 유료 서비스 검증이 아니다. 먼저 운영비를 최소화한 무료 개인 도구로 본인이 매주 반복 사용하고, 이후 소규모 초대 사용자로 재방문과 저장 습관을 검증한다.

## 2. 확정된 제품 방향

- MVP는 수동 작성, 텍스트 붙여넣기, 링크 메타데이터 수집을 제공한다.
- 규칙 기반 정리만 자동화한다. 원문에 없는 분량·시간·온도는 만들지 않는다.
- 사용자가 결과를 검토·수정한 뒤 저장한다. 자동 저장하지 않는다.
- Google 로그인만 구현한다. 초기에는 허용된 계정만 접근할 수 있고, 나중에 공개 가입을 열 수 있게 다중 사용자 구조로 만든다.
- 모든 사용자의 데이터는 기본 비공개다.
- 무료 플랜을 우선한다. MVP에는 광고, 결제, OpenAI API 호출을 넣지 않는다.
- 향후 AI 정리는 보상형 광고 시청으로 1회 이용권을 발급하는 후보 기능으로만 설계한다. 광고 수익이 분석 비용을 감당하는지 검증하기 전에는 약속하지 않는다.
- Kakao 로그인, 챗봇, 커뮤니티, 장보기 목록, 인분 자동 계산, 앱스토어 배포는 MVP 범위 밖이다.

## 3. 사용자 흐름

### 로그인

1. 사용자가 Google로 로그인한다.
2. 초기 허용 목록에 없는 계정은 접근 거부 화면을 본다.
3. 유효한 세션이면 보관함으로 이동한다.
4. 세션이 만료되면 저장하지 않은 입력을 보존할 수 있는 안내와 함께 로그인으로 이동한다.

### 줍줍하기

입력 방식은 링크 가져오기, 텍스트 붙여넣기, 직접 작성 중 하나다.

- 링크 입력은 URL 형식과 허용 플랫폼을 먼저 검사한다.
- 접근 가능한 제목·작성자·플랫폼·설명문만 수집한다.
- 링크를 읽지 못하면 실패 원인과 캡션 붙여넣기, 참고 파일 첨부, 직접 작성, 링크만 출처로 남기기 선택지를 보여준다.
- 텍스트와 직접 작성은 제목, 정보 유형, 본문, 태그, 출처 유형, 선택적 원본 URL과 첨부 파일을 받는다.
- 같은 원본 URL이 이미 있으면 기존 항목을 안내하고 재분석이 아닌 새 항목 저장 여부를 사용자가 결정한다.

### 규칙 기반 정리

다음처럼 설명 가능한 보조만 제공한다.

- 번호가 있는 줄을 조리 단계 후보로 인식
- `재료`, `준비물`, `ingredients`와 같은 구분 제목 아래를 목록 후보로 인식
- 연속 공백과 불필요한 줄바꿈 정리
- 첫 줄 또는 짧은 문장을 제목 후보로 제안

후보는 항상 편집 가능한 초안이다. 빈 값은 `미기재`, 추출 실패는 `추출 실패`, 충돌한 값은 각각의 근거와 함께 `확인 필요`로 구분한다.

## 4. 화면과 상태

### 보관함

- 최근 저장순 카드 목록
- 제목·본문·태그·유형별 내용 검색
- 태그 필터, 즐겨찾기 필터
- 정보 유형, 제목, 태그, 출처, 저장일, 대표 이미지 또는 기본 그림을 공통 카드에 표시
- 빈 상태, 로딩 스켈레톤, 재시도 가능한 오류 상태 제공

### 결과 확인

- 공통 필드와 유형별 필드를 모두 편집
- 원문과 정리된 내용을 분리해 표시
- 누락·충돌·미확인 근거 표시
- 태그 추가·삭제
- 저장 전 미리보기
- 저장 중 중복 제출 방지와 이탈 경고

### 상세

- 내용 열람, 원본 링크, 출처 근거, 개인 메모
- 태그와 즐겨찾기 수정
- 수정·삭제
- 삭제는 확인 후 DB 레코드와 연결 첨부 파일을 함께 제거

### 공통 상태 규칙

- 완료되지 않은 작업은 완료로 표시하지 않는다.
- 네트워크 오류가 나도 입력 내용을 유지한 채 재시도한다.
- 반복 클릭은 같은 처리 작업을 여러 번 만들지 않는다.
- 자동 후보와 사용자가 직접 입력한 값을 구분한다.
- 장식이나 마스코트가 필수 정보를 대신하지 않는다.

## 5. 확장 가능한 데이터 모델

정보 항목을 중심으로 하고 레시피는 첫 번째 유형으로 둔다.

### 공통 테이블

- `profiles`: Auth 사용자와 앱 프로필의 연결, 표시 이름, 계정 상태
- `access_allowlist`: 초기 운영에서 허용할 Google 식별자를 보관하는 보호된 접근 목록
- `items`: `id`, `user_id`, `type`, `title`, `summary`, `favorite`, `notes`, `created_at`, `updated_at`, `schema_version`
- `item_contents`: 검색·열람용 정리 본문
- `sources`: 원본 URL, 플랫폼, 작성자, 출처 유형, 수집 방식
- `source_evidence`: 원문 조각, 근거 위치, 누락·충돌·확인 상태
- `attachments`: Storage 경로, MIME 유형, 크기, 보관 상태
- `tags`: 사용자 소유의 태그 이름
- `item_tags`: 항목과 태그의 다대다 연결
- `processing_jobs`: 규칙 기반 또는 향후 AI 작업의 상태와 오류

`profiles`와 `access_allowlist`를 제외한 사용자 데이터 테이블은 모두 명시적인 `user_id`를 가진다. `sources`, `source_evidence`, `attachments`, `item_tags`도 연결된 항목만으로 권한을 추론하지 않고 사용자 범위를 함께 검사한다. 향후 AI 이용권은 `usage_grants`를 별도 추가하되 MVP 스키마에는 포함하지 않는다.

### 유형별 테이블

- `recipe_details`: 인분, 준비·조리 시간, 온도, 팁
- `ingredients`: 재료명, 분량 원문, 순서, 확인 상태
- `recipe_steps`: 단계 번호, 조리 내용, 시간·온도 근거

향후 정보 유형은 필요한 필드만 별도 테이블로 추가한다. 공통 데이터와 유형별 데이터를 하나의 거대한 JSON이나 빈 필드 묶음으로 합치지 않는다.

## 6. 보안 설계

- 모든 공통·유형별·연결 테이블에 `user_id` 기반 PostgreSQL RLS를 적용한다.
- 비로그인 사용자는 개인 데이터에 접근할 수 없다.
- 사용자는 자신의 행만 조회·생성·수정·삭제할 수 있다.
- 태그도 사용자 소유로 제한하고 다른 사용자의 태그 ID를 연결할 수 없게 한다.
- Storage는 비공개 버킷만 사용하고 객체 경로는 `{user_id}/{item_id}/...`로 분리한다.
- 파일 조회·삭제는 소유자 정책을 통과한 경우에만 허용한다.
- 서비스 키는 서버 전용이며 일반 사용자 CRUD에서 RLS 우회 목적으로 사용하지 않는다.
- Google 계정 허용 목록은 사용자 편집 가능 메타데이터가 아니라 서버 측 설정 또는 보호된 테이블로 관리한다.
- URL 수집은 허용된 플랫폼과 안전한 리디렉션만 처리하고 내부 주소·사설 IP·임의 프로토콜 접근을 차단한다.
- 업로드 MIME 유형, 파일 크기, 파일 개수, 처리 길이를 제한한다. 사용자 파일명을 경로로 신뢰하지 않는다.
- 외부 콘텐츠의 명령문은 데이터로만 취급하며 서비스 동작 지시로 실행하지 않는다.
- 로그에 이메일, 원문 전체, 인증 토큰, 서비스 키를 남기지 않는다.
- 모든 RLS 정책에 본인 허용, 다른 사용자 거부, 비로그인 거부 테스트를 둔다.
- 비밀값은 GitHub에 커밋하지 않고 배포 환경의 Secret 변수로만 관리한다.

## 7. 기술 구성과 경계

- 프론트엔드·라우팅: Next.js App Router
- 서버 API: Next.js Route Handlers
- 인증·DB·Storage: Supabase Auth, PostgreSQL, Storage
- 배포: GitHub와 연결한 Vercel
- 초기 도메인 후보: `chagok.vercel.app`

코드 경계:

- `app/`: 화면과 라우팅
- `components/`: 재사용 UI
- `lib/auth/`: Google 로그인·세션
- `lib/data/`: Supabase 조회·저장
- `lib/normalizers/`: 입력을 공통 `item` 구조로 변환
- `lib/extractors/`: 플랫폼별 메타데이터 수집
- `lib/rules/`: 규칙 기반 후보 정리
- `lib/ai/`: 현재 비활성인 AI 제공자 인터페이스
- `supabase/migrations/`: 스키마·인덱스·RLS
- `supabase/tests/`: 데이터 접근 정책 테스트

파일은 브라우저에서 비공개 Storage로 직접 업로드하고, API에는 메타데이터와 제한된 처리 요청만 보낸다. 긴 영상 분석은 MVP에 포함하지 않으며, 향후 `processing_jobs` 기반 비동기 작업으로 별도 구성한다.

## 8. 개발 단계와 완료 기준

1. Next.js 기본 앱과 모바일 레이아웃
2. Google 로그인과 초기 허용 목록
3. Supabase 스키마·마이그레이션·RLS·접근 테스트
4. 보관함·검색·태그·즐겨찾기
5. 직접 작성·텍스트 붙여넣기·결과 확인·상세·수정·삭제
6. 링크 메타데이터 수집과 실패 처리
7. 비공개 Storage 첨부
8. 대표 고구마 누룽지 자료로 원문 근거와 미기재 값 검증
9. Vercel 배포와 모바일·PC 재접속 검증

완료 조건은 다음과 같다.

- 한 사용자가 휴대폰에서 자료를 입력·수정·저장하고 PC에서 다시 찾을 수 있다.
- 제목·본문·태그·유형별 필드로 검색할 수 있다.
- 링크 수집 실패, 누락, 충돌, 중복 제출이 정직하게 표시된다.
- 다른 사용자와 비로그인 사용자는 데이터에 접근할 수 없다.
- API 키·서비스 키·개인 원문이 클라이언트 번들, GitHub, 로그에 노출되지 않는다.
- 테스트 자료에서 재료 분량 미기재와 예열 여부 미확인을 추측 없이 보존한다.

## 9. 향후 AI와 수익화 경계

AI 기능은 MVP 이후 선택 기능이다. `lib/ai/`의 제공자 인터페이스와 `processing_jobs`, `usage_grants`만 먼저 고려한다.

후보 흐름:

1. 사용자가 AI 정리를 선택
2. 보상형 광고 시청 완료 확인
3. 사용자·항목·작업에 연결된 1회 이용권 발급
4. 비용·시간·실패를 기록한 비동기 분석 실행
5. 결과를 검토 화면에 표시하고 사용자가 저장

광고 수익이 API 비용과 운영비를 감당하는지, 사용자당 일일 한도와 실패 시 이용권 환불 규칙을 검증하기 전에는 공개 기능으로 약속하지 않는다. AI가 없어도 수동 작성과 기존 데이터 열람은 항상 동작한다.
