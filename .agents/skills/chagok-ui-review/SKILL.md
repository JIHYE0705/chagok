# 차곡 UI 검토

저장소 루트의 `docs/design/DESIGN_SYSTEM.md`와 `docs/design/DECISIONS.md`를 읽는다. 현재 화면과 과거 #34 시안을 구분하고 최신 사용자 승인 범위에 맞춰 검토한다. 문서상의 목표를 이미 구현된 기능으로 간주하지 않는다.

- 음식 사진·레시피 제목·재료/단계가 먼저 읽히는가? 노란색·파스텔·캐릭터·큰 둥근 박스·스티커가 내용을 압도하지 않는가?
- 공통 토큰·타입 크기·굵기·간격·반경이 일관되는가? Olive Gray를 Vanilla 위 일반 텍스트에 쓰지 않았는가? 노란 컨트롤의 경계·선택 상태를 색 채움에만 의존하지 않는가?
- 320px~PC, 긴 한글 제목/단계, 수치·단위, 사진 유무에서 읽고 조작할 수 있는가? 목록 제목의 표시 제한이 저장 원문이나 상세 내용을 자르지 않는가?
- 일반 텍스트 4.5:1, 필요한 UI 경계·상태 3:1, 포커스·키보드·44px 조작 영역·확대·reduced-motion을 해당 변경에 맞게 확인했는가?
- 카드/목록 전환·기억, 검색·필터·페이지, 저장/수정, 실패 후 입력 보존·이탈 경고·덮어쓰기 확인, 출처/근거·첨부/표지 보기가 유지되는가?
- `success | partial | failed`, 미기재와 확인 필요가 유지되는가? 공개 메타데이터나 테스트 콘텐츠를 검증된 레시피로 표현하지 않는가?
- 필수/선택 항목과 저장 중/완료/오류가 명확한가? 없는 분량 계산·버전 이력 등 새 기능을 디자인 수정에 섞지 않았는가?

변경된 화면과 연결 컴포넌트를 읽고 관련 항목만 검증한다. 새 화면·대규모 리디자인은 방향을 먼저 제안하고 승인된 범위에서 진행한다. 단순 수정에는 과도한 재설계를 요구하지 않는다.

결과에는 파일·화면 근거, 사용자에게 미치는 영향, 최소 수정 권고와 우선순위를 남긴다. 실제 브라우저·단색 계산·과거 캡처 관찰을 구분하고 미실행한 실기기·외부 로그인·저장 회귀 등을 명시한다. 자동 검사 통과만으로 전체 접근성 또는 디자인 완성을 선언하지 않는다.
